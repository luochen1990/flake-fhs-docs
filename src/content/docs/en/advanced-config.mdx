This chapter introduces the `mkFlake` global configuration in `flake.nix` and settings for other tools (such as Formatter).

## mkFlake Configuration

The `mkFlake` function is the entry point of the framework. It accepts two arguments: context (`inputs`, `self`, etc.) and configuration module.

A typical `flake.nix` configuration looks like this:

```nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    flake-fhs.url = "github:luochen1990/flake-fhs";
  };

  outputs = inputs@{ flake-fhs, ... }:
    flake-fhs.lib.mkFlake { inherit inputs; } {
      # 1. Set supported systems (optional)
      systems = [ "x86_64-linux" "aarch64-darwin" ];

      # 2. Configure nixpkgs instance (optional)
      nixpkgs.config = {
        allowUnfree = true;
      };
      
      # 3. flake-parts-like flake options (optional)
      # For adding non-standard flake outputs or manual extension
      flake = {
        # overlays.default = ...
      };
    };
}
```

### Common Configuration Options

| Option | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `systems` | list | standard systems | List of supported system architectures (x86_64-linux, aarch64-darwin, etc.) |
| `nixpkgs.config` | attrs | `{ allowUnfree = true; }` | Configuration passed to nixpkgs |
| `layout.roots` | list | `["" "/nix"]` | List of project root directories. Supports aggregating content from multiple directories. |
| `systemContext` | lambda | `_: {}` | System context generator (`system -> attrs`). The `specialArgs` in the returned attrset will be passed to `nixosSystem`. Supports automatic merging. |
| `flake` | attrs | `{}` | Merged into generated flake outputs. Used to manually extend or override FHS generated content. |

### Layout Configuration

You can customize the source directory for each type of output via the `layout` option. For example:

```nix
layout.packages.subdirs = [ "pkgs" "my-packages" ];
```

This means the framework will scan both `pkgs/` and `my-packages/` directories to look for package definitions.

#### Module Layout Options

| Option | Default | Description |
| :--- | :--- | :--- |
| `layout.nixosModules.subdirs` | `[ "nixosModules" "modules" ]` | List of directories to scan for NixOS modules |
| `layout.nixosModules.guardedSuffix` | `".cfg.nix"` | File suffix for guarded config files. See [Modules Guide](../manual-modules/#custom-suffix) |
| `layout.nixosModules.strictOptions` | `false` | Enable Strict Options Validation (see below) |

## Strict Options Validation

By default, the framework **does not enforce** option namespace alignment. When enabled, the framework validates that each directory module's `default.nix` defines option paths matching its directory structure.

### Enabling

```nix
{
  outputs = inputs@{ flake-fhs, ... }:
    flake-fhs.lib.mkFlake { inherit inputs; } {
      layout.nixosModules.strictOptions = true;
    };
}
```

### Validation Rules

When enabled, options defined in each directory module must be prefixed by their directory path:

```nix
# modules/foo/default.nix
{ lib, ... }:
{
  options.foo = {  # ✅ Matches directory path foo
    setting = lib.mkOption { ... };
  };
}

# modules/foo/bar/default.nix
{ lib, ... }:
{
  options.foo.bar = {  # ✅ Matches directory path foo/bar
    setting = lib.mkOption { ... };
  };
}
```

<Aside type="caution" title="Behavior on Violations">
When `strictOptions = true` and a namespace mismatch exists, it does **not** error at flake evaluation time. Instead, violations are reported via `config.assertions` at system evaluation time. This means you need to actually build a NixOS configuration to see validation results.
</Aside>

## Module System Design Rationale

This section explains the key design decisions behind the module system to help you understand the framework's behavior.

### Module Entry Convention

The framework has a single module entry convention: `default.nix` (directory module) or a standalone `.nix` file (single-file module).

| Concept | Identifier | Enable Mechanism | Nesting |
| :--- | :--- | :--- | :--- |
| Directory Module | Directory with `default.nix` | Unconditionally injected | Supported (enable-chain) |
| Single File Module | Standalone `.nix` (outside directory module subtrees) | None | — |
| Guarded Config File | `.cfg.nix` suffix | Wrapped with `mkIf (enable-chain)` | — |

### Key Design Decisions

<Aside type="note" title="Why Does nixosModules.default Include All Modules?">
Following the **Zero-boilerplate** principle. Users only need one line — `imports = [ flake.nixosModules.default ]` — to import all modules, then enable directory modules as needed. This is simpler than selective imports and requires no additional partial loading mechanism.
</Aside>

<Aside type="note" title="Why No Partial Loading?">
Partial loading (selectively loading modules) would introduce significant implementation complexity for very few real-world use cases. The `nixosModules.default` approach — including all modules — is simpler, and users can still import specific modules individually via `flake.nixosModules.<name>`.
</Aside>

## Formatter - Code Formatting

Flake FHS configures `formatter` output by default, supporting the `nix fmt` command.

### Automatic Detection

Flake FHS integrates `treefmt`. It automatically detects configuration files under the root directory with the following priority:

1.  **`treefmt.nix`**: Preferred. If `inputs` contains `treefmt-nix`, it integrates via that library; otherwise loads Nix configuration directly.
2.  **`treefmt.toml`**: Uses this TOML file as configuration.
3.  **No configuration file**: Directly uses default `pkgs.treefmt`.

### Usage

```bash
# Format all files in the project
nix fmt
```
