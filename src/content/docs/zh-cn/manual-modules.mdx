`modules/` 目录用于组织可复用的 NixOS 模块。系统根据目录结构自动发现模块，无需手动维护 `module-list.nix`。

模块系统的核心概念只有两个：

- **模块**：唯一的入口约定——目录有 `default.nix` 即为目录模块，独立的 `.nix` 文件（且不在任何目录模块子树内）即为单文件模块
- **guarded 配置文件**（`.cfg.nix`）：一个文件级属性。它的内容会被 `mkIf (enable-chain)` 包裹，由所属目录模块自动 import

## 模块种类

### 目录模块 (Directory Module)

**识别标识**：目录包含 `default.nix`

**特点**：
- `default.nix` 是模块入口，可写 options 和 config
- **无条件注入** `<modPath>.enable` 选项（若未手动定义）——这是 enable-chain 自洽的前提
- `default.nix` 中的 config **总是生效**（不被 `mkIf` 包裹）
- 支持嵌套，子模块的 enable-chain 包含所有祖先模块的 enable

**示例**：
```
modules/tweaks/
├── default.nix  # options.tweaks.* + 基础 config（总是生效）
└── utils.nix    # 辅助文件，由 default.nix 显式 import
```

### 单文件模块 (Single File Module)

**识别标识**：独立的 `.nix` 文件，且**不在任何目录模块的子树内**

**特点**：
- 直接导出，无 enable 注入，无 enable-chain
- 位于目录模块子树内的 `.nix` 文件（除 `.cfg.nix`）**不会**被识别为单文件模块，由该目录模块的 `default.nix` 手动管理

**示例**：
```
modules/
├── utils.nix          # ✅ 单文件模块（不在任何目录模块子树内）
├── network/           # 目录模块
│   ├── default.nix
│   └── helpers/
│       └── util.nix   # ❌ 不是单文件模块（在 network 目录模块子树内，需 default.nix 手动 import）
└── misc/
    └── helper.nix     # ✅ 单文件模块（misc 不在任何目录模块子树内）
```

## guarded 配置文件 (.cfg.nix)

**识别标识**：文件名匹配配置的后缀（默认 `.cfg.nix`，可通过 `layout.nixosModules.guardedSuffix` 自定义）

**位置约束**：必须位于某个目录模块的子树内

**行为**：
- 内容被 `mkIf (enable-chain)` 包裹（无需手动写 `mkIf`）
- 由所属目录模块自动 import

### 为什么需要 .cfg.nix？

NixOS 模块鼓励将复杂配置拆分到多个文件中以便维护。但在传统写法里，每个拆分出来的文件都需要重复写一遍 `lib.mkIf cfg.enable { ... }` 来受开关控制——这是纯粹的样板代码。

`.cfg.nix` 机制让拆分变得零成本：你只需把受开关控制的配置放进 `.cfg.nix` 文件，框架自动包裹 `mkIf` 并自动 import，无需任何重复工作。

对比：

```nix
# ❌ 传统写法：每个拆分文件都要手写 mkIf
# modules/web-server/service.nix
{ config, lib, ... }:
let cfg = config.services.web-server;
in {
  config = lib.mkIf cfg.enable {
    systemd.services.web-server = { /* ... */ };
  };
}

# modules/web-server/firewall.nix
{ config, lib, ... }:
let cfg = config.services.web-server;
in {
  config = lib.mkIf cfg.enable {
    networking.firewall.allowedTCPPorts = [ cfg.port ];
  };
}
```

```nix
// ✅ .cfg.nix 写法：框架自动包裹 mkIf，自动 import
# modules/web-server/service.cfg.nix
{ config, ... }: {
  systemd.services.web-server = { /* ... */ };  # 无需手写 mkIf
}

# modules/web-server/firewall.cfg.nix
{ config, ... }: {
  networking.firewall.allowedTCPPorts = [ config.services.web-server.port ];
}
```

### enable-chain 精确定义

一个 `.cfg.nix` 的 `mkIf` 条件 = 链路上**所有祖先模块**（有 `default.nix` 的祖先目录）的 enable AND **自身所属模块**的 enable 之 AND。

中间目录若无 `default.nix`（只是路径组织用），不参与 enable-chain，但仍贡献 modPath 段。

### 自定义后缀

默认后缀是 `.cfg.nix`，可通过 `layout.nixosModules.guardedSuffix` 自定义：

```nix
{
  outputs = inputs@{ flake-fhs, ... }:
    flake-fhs.lib.mkFlake { inherit inputs; } {
      layout.nixosModules.guardedSuffix = ".guarded.nix";
    };
}
```

## 使用方法

### 使用模块

在 `hosts/my-machine/configuration.nix` 中：

```nix
{
  # 所有模块都已通过 nixosModules.default 自动导入
  # 目录模块的 enable 选项可按需开启
  services.web-server.enable = true;
  services.web-server.port = 9000;
}
```

### 定义目录模块（含 guarded 配置）

以 `modules/services/web-server` 为例：

**1. `default.nix`：定义 options 和基础 config**

<Aside type="tip" title="自动 Enable">
所有目录模块都会自动注入 `<modPath>.enable` 选项（若未手动定义）。你也可以手动定义以自定义描述文字。
</Aside>

<Aside type="tip" title="选项命名空间">
默认情况下，选项的命名空间不受强制约束。如果希望框架自动校验选项路径与目录结构是否匹配，请参阅 [高级配置](../advanced-config/#strict-options-validation) 中的 Strict Options Validation。
</Aside>

```nix
# modules/services/web-server/default.nix
{ lib, ... }:
{
  options.services.web-server = {
    port = lib.mkOption {
      type = lib.types.port;
      default = 8080;
    };
  };
}
```

**2. `*.cfg.nix`：定义受开关控制的 config**

```nix
# modules/services/web-server/service.cfg.nix
{ config, pkgs, ... }:
{
  # 无需手写 config = lib.mkIf cfg.enable { ... }
  # 框架已自动包裹

  systemd.services.web-server = {
    description = "Simple Python Web Server";
    wantedBy = [ "multi-user.target" ];
    serviceConfig = {
      ExecStart = "${pkgs.python3}/bin/python -m http.server ${toString config.services.web-server.port}";
      Restart = "always";
    };
  };
}
```

**3. 继续拆分更多 `.cfg.nix`**

```nix
# modules/services/web-server/firewall.cfg.nix
{ config, lib, ... }:
{
  networking.firewall.allowedTCPPorts = lib.mkIf config.services.web-server.openFirewall
    [ config.services.web-server.port ];
}
```

### 定义单文件模块

最简单的模块形式，直接编写配置：

```nix
# modules/personal-config.nix
{ config, lib, ... }:
{
  # 直接定义配置，无 enable 机制
  users.users.alice = {
    isNormalUser = true;
    extraGroups = [ "wheel" ];
  };
}
```

## 输出结构

### 单个模块输出

每个模块生成一个 `nixosModules.<path>` 输出：

| 目录 | 输出 |
| :--- | :--- |
| `modules/web-server/` | `nixosModules.services/web-server` |
| `modules/utils.nix` | `nixosModules.utils` |

### 默认模块

`nixosModules.default` 包含**所有**模块：

- 所有目录模块（含 enable 注入和 `.cfg.nix` 的 mkIf 守卫）
- 所有单文件模块（直接生效）

```nix
{
  # 一次性导入所有模块
  imports = [ flake.nixosModules.default ];

  # 按需启用目录模块的 enable
  services.web-server.enable = true;
}
```

## 设计决策

<Aside type="note" title="为什么所有目录模块都注入 enable？">
因为 enable-chain 的自洽性要求链路上每个模块都有 enable。如果只对"含 `.cfg.nix` 的模块"注入 enable，那么当某个无 `.cfg.nix` 的祖先模块出现在链路上时，子孙 `.cfg.nix` 的 mkIf 条件会引用一个不存在的 option 而出错。无条件注入是最简单、最自洽的设计。
</Aside>

<Aside type="note" title="nixosModules.default 包含什么？">
所有模块（目录模块 + 单文件模块），遵循 **零样板 (Zero-boilerplate)** 原则。用户只需 `imports = [ flake.nixosModules.default ]` 即可导入全部模块，然后按需启用目录模块的 `enable`。
</Aside>
