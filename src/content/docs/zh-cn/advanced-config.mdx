## mkFlake 配置

`mkFlake` 函数是框架的入口，它接受两个参数：上下文 (`inputs`, `self` 等) 和 配置模块。

一个典型的 `flake.nix` 配置如下：

```nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    flake-fhs.url = "github:luochen1990/flake-fhs";
  };

  outputs = inputs@{ flake-fhs, ... }:
    flake-fhs.lib.mkFlake { inherit inputs; } {
      # 1. 设置支持的系统 (可选)
      systems = [ "x86_64-linux" "aarch64-darwin" ];

      # 2. 配置 nixpkgs 实例 (可选)
      nixpkgs.config = {
        allowUnfree = true;
      };
      
      # 3. 类似 flake-parts 的 flake 选项 (可选)
      # 用于添加非标准的 flake outputs 或进行手动扩展
      flake = {
        # overlays.default = ...
      };
    };
}
```

### 常用配置项

| 选项 | 类型 | 默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `systems` | list | standard systems | 支持的系统架构列表 (x86_64-linux, aarch64-darwin 等) |
| `nixpkgs.config` | attrs | `{ allowUnfree = true; }` | 传递给 nixpkgs 的配置 |
| `layout.roots` | list | `["" "/nix"]` | 项目根目录列表。支持从多个目录聚合内容。 |
| `systemContext` | lambda | `_: {}` | 系统上下文生成器 (`system -> attrs`)。返回的 attrset 中的 `specialArgs` 将被传递给 `nixosSystem`。支持自动合并。 |
| `flake` | attrs | `{}` | 合并到生成的 flake outputs 中。用于手动扩展或覆盖 FHS 生成的内容。 |

### 布局配置 (Layout)

你可以通过 `layout` 选项自定义各类型 output 的源目录。例如：

```nix
layout.packages.subdirs = [ "pkgs" "my-packages" ];
```

这意味着框架将同时扫描 `pkgs/` 和 `my-packages/` 目录来寻找包定义。

#### 模块布局选项

| 选项 | 默认值 | 说明 |
| :--- | :--- | :--- |
| `layout.nixosModules.subdirs` | `[ "nixosModules" "modules" ]` | 扫描 NixOS 模块的目录列表 |
| `layout.nixosModules.suffix` | `".nix"` | Guarded 模块自动导入配置文件的后缀。详见 [模块手册](../manual-modules/#自定义文件后缀) |
| `layout.nixosModules.strictOptions` | `false` | 是否启用 Strict Options Validation（详见下文） |

## Strict Options Validation

默认情况下，框架**不强制**校验选项的命名空间。启用后，框架会检查每个 Guarded 模块的 `options.nix` 中定义的选项路径是否与目录结构匹配。

### 启用方式

```nix
{
  outputs = inputs@{ flake-fhs, ... }:
    flake-fhs.lib.mkFlake { inherit inputs; } {
      layout.nixosModules.strictOptions = true;
    };
}
```

### 校验规则

启用后，每个 `options.nix` 中定义的选项必须在对应目录路径下：

```nix
# modules/foo/options.nix
{ lib, ... }:
{
  options.foo = {  # ✅ 匹配目录路径 foo
    setting = lib.mkOption { ... };
  };
}

# modules/foo/bar/options.nix
{ lib, ... }:
{
  options.foo.bar = {  # ✅ 匹配目录路径 foo/bar
    setting = lib.mkOption { ... };
  };
}
```

<Aside type="caution" title="违规时的行为">
当 `strictOptions = true` 且存在命名空间不匹配时，**不会**在 flake 求值时报错，而是在系统求值时通过 `config.assertions` 报告违规。这意味着你需要实际构建一个 NixOS configuration 才能看到校验结果。
</Aside>

## 模块系统设计原理

本节解释模块系统背后的关键设计决策，帮助你理解框架的行为逻辑。

### 三种互斥的模块类型

框架将模块分为三种类型：**Single File**、**Traditional**、**Guarded**。它们是互斥的——每种目录结构对应且仅对应一种模块类型：

| 类型 | 识别标识 | Enable 机制 | 嵌套 |
| :--- | :--- | :--- | :--- |
| Single File | 独立 `.nix` 文件 | 无 | — |
| Traditional | 目录含 `default.nix` | 无 | 不支持 |
| Guarded | 目录含 `options.nix` | 自动生成 | 支持 |

### 关键设计决策

<Aside type="note" title="为什么 nixosModules.default 包含所有模块？">
遵循 **零样板 (Zero-boilerplate)** 原则。用户只需一行 `imports = [ flake.nixosModules.default ]` 即可导入全部模块，然后按需启用 Guarded 模块的 `enable`。这比按需手动导入更简单，且不需要额外的 partial loading 机制。
</Aside>

<Aside type="note" title="为什么 Traditional 模块不支持嵌套？">
Traditional 模块被设计为**封装的 (encapsulated)**——它们自行管理 imports，与 nixpkgs 上游的 `default.nix` 约定一致。如果允许嵌套，会导致模块边界模糊（子目录的 `default.nix` 究竟是独立模块还是父模块的一部分？），增加理解负担。需要嵌套时应使用 Guarded 模块。
</Aside>

<Aside type="note" title="为什么不支持 Partial Loading？">
Partial Loading（选择性加载模块）会引入显著的实现复杂度，且实际使用场景极少。`nixosModules.default` 包含所有模块的方案更简单，用户仍可通过 `flake.nixosModules.<name>` 单独导入特定模块。
</Aside>

## Formatter - 代码格式化

Flake FHS 默认配置了 `formatter` 输出，支持 `nix fmt` 命令。

### 自动检测

Flake FHS 集成了 `treefmt`。它会自动检测根目录下的配置文件，优先级如下：

1.  **`treefmt.nix`**: 优先使用。若 `inputs` 中包含 `treefmt-nix`，则通过该库集成；否则直接加载 Nix 配置。
2.  **`treefmt.toml`**: 使用该 TOML 文件作为配置。
3.  **无配置文件**: 直接使用默认的 `pkgs.treefmt`。

### 使用方法

```bash
# 格式化项目中的所有文件
nix fmt
```
